## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速掌握平台状态 (Priority: P1)

作为管理员，我可以从管理后台看到用户与核心业务使用情况的汇总，并进入需要处理的用户范围，从而快速发现账号异常和运营变化。

**Why this priority**: 管理员首先需要知道平台当前发生了什么，才能决定是否以及对谁采取后续操作。

**Independent Test**: 准备包含普通用户、管理员、禁用用户以及不同业务使用量的数据集，登录管理后台后核对摘要、状态分布和近期变化是否准确，并验证无数据与数据加载失败时仍能理解页面状态。

**Acceptance Scenarios**:

1. **Given** 平台存在不同角色和状态的用户，**When** 管理员打开后台首页，**Then** 系统展示用户总数、有效用户数、禁用用户数、管理员数，以及投递和面经的全局数量。
2. **Given** 平台在最近 7 天和 30 天内存在新注册或活跃用户，**When** 管理员查看后台首页，**Then** 系统展示对应时间范围的新增与活跃趋势，并明确标注统计口径和更新时间。
3. **Given** 某项统计没有数据或暂时无法取得，**When** 页面展示摘要，**Then** 系统分别显示可辨识的空状态或失败状态，不把未知值显示为零。
4. **Given** 普通用户或未登录访客尝试访问后台，**When** 系统校验访问者身份，**Then** 不展示任何管理数据，并将访问者带到其有权访问的页面或给出明确拒绝结果。

---

### User Story 2 - 定位并了解用户 (Priority: P1)

作为管理员，我可以按账号信息、角色和状态检索用户，并查看单个用户的账号资料、活动摘要和安全状态，从而在大量账号中快速找到需要处理的对象。

**Why this priority**: 现有分页列表不足以支撑规模化管理；可靠定位目标是所有账号操作的前提。

**Independent Test**: 在至少 10,000 个用户的代表性数据集中，分别使用精确账号、部分账号、角色、状态和组合条件检索，再打开用户详情，核对结果、总数、分页、空状态及活动摘要。

**Acceptance Scenarios**:

1. **Given** 用户目录包含多个相似账号，**When** 管理员输入用户名或内部邮箱的完整或部分文本，**Then** 系统只返回匹配用户并保留当前筛选条件。
2. **Given** 用户具有不同角色和账号状态，**When** 管理员组合选择角色与状态筛选，**Then** 列表、结果总数和分页均使用相同条件。
3. **Given** 管理员打开某个用户详情，**When** 详情加载完成，**Then** 系统展示账号标识、角色、状态、注册时间、最近登录时间、投递数量、面经数量和最近账号变更记录。
4. **Given** 检索无匹配结果，**When** 管理员查看列表，**Then** 系统显示明确空状态，并提供清除筛选的操作。
5. **Given** 管理员刷新、翻页或从详情返回列表，**When** 返回用户目录，**Then** 原有检索、筛选和页码状态得到保留。

### User Story 3 - 安全地管理账号访问 (Priority: P2)

作为管理员，我可以授予或撤销管理员角色、禁用或重新启用普通账号，并在操作前确认影响、填写原因，从而解决访问问题且避免误操作或锁死后台。

**Why this priority**: 账号访问变更影响安全和用户可用性，需要在检索能力完善后提供更清晰、更可追责的操作流程。

**Independent Test**: 使用两个有效管理员、一个普通用户和一个已禁用用户，执行全部角色与状态变更，验证确认信息、原因校验、即时结果、会话失效、重复提交防护以及最后管理员保护。

**Acceptance Scenarios**:

1. **Given** 管理员准备变更用户角色或状态，**When** 发起操作，**Then** 系统展示目标账号、当前值、变更后值和影响，并要求输入操作原因后才能确认。
2. **Given** 管理员确认禁用一个有效普通用户，**When** 变更成功，**Then** 目标用户的现有登录立即失效、后续登录被拒绝，列表和详情同步显示新状态。
3. **Given** 管理员重新启用已禁用用户，**When** 变更成功，**Then** 目标用户可再次登录，但禁用前的登录状态不会自动恢复。
4. **Given** 操作将禁用或降级最后一个有效管理员，**When** 管理员尝试确认，**Then** 系统拒绝操作、说明原因，并保持账号原状。
5. **Given** 管理员尝试禁用或降级自己的当前账号，**When** 仍存在其他有效管理员，**Then** 系统进行强化确认并在成功后立即结束当前管理会话。
6. **Given** 同一账号已被另一位管理员变更，**When** 当前管理员基于旧状态提交操作，**Then** 系统拒绝覆盖新状态、提示数据已变化，并要求刷新后重新确认。
7. **Given** 变更提交失败或结果未知，**When** 系统返回反馈，**Then** 页面保留管理员填写的原因、明确说明未确认成功，并允许在核对当前状态后安全重试。

### User Story 4 - 审查管理操作 (Priority: P3)

作为管理员，我可以查看不可由后台界面修改的管理审计记录，并按操作者、目标用户、事件类型和时间范围筛选，从而调查账号变更、确认责任和发现异常操作。

**Why this priority**: 审计提升治理和排障能力，但不阻挡基础的查看、检索与账号处置流程。

**Independent Test**: 执行成功、被保护规则拒绝和并发冲突三类管理操作，再在审计页按各维度筛选，核对记录的操作者、目标、变更前后值、原因、结果和时间。

**Acceptance Scenarios**:

1. **Given** 管理员完成或尝试角色与状态变更，**When** 打开审计记录，**Then** 系统展示事件时间、操作者、目标用户、操作类型、变更前后值、原因和结果。
2. **Given** 审计记录数量较多，**When** 管理员按操作者、目标用户、事件类型、结果或时间范围筛选，**Then** 系统仅展示符合全部条件的记录并给出结果总数。
3. **Given** 用户账号标识后来发生变化，**When** 管理员查看历史记录，**Then** 记录仍能辨认事件发生时的操作者和目标账号，并可关联到仍存在的当前用户。
4. **Given** 管理员使用后台，**When** 查看审计记录，**Then** 不存在编辑或删除审计事件的操作。

### Edge Cases

- 用户在列表加载后被删除或变为不可管理状态时，详情和操作应提示记录已不存在或不可操作，不能继续使用陈旧数据。
- 搜索文本仅含空格、过长或含特殊字符时，系统应规范化输入、限制长度并给出可理解的结果，不产生越权或异常查询。
- 筛选条件指向不存在的页码时，系统应回到最后一个有效页或空结果的第一页，并保留筛选条件。
- 两位管理员同时修改同一用户时，后提交者不得无提示覆盖先提交者的结果。
- 目标用户正处于登录或写入业务数据过程中时，禁用操作仍应确定性完成；禁用成功后的新请求必须被拒绝。
- 活跃用户统计遇到从未登录、会话已过期或账号已禁用的用户时，应按页面公布的统一口径计算。
- 平台只有一个有效管理员时，任何会导致零个有效管理员的自我操作都必须被阻止。
- 审计记录引用的操作者或目标用户已不存在时，历史事件仍必须可读，且明确标注账号已删除。
- 管理后台在窄桌面或移动视口下，应允许完整读取表格信息和完成关键操作，不依赖横向内容被截断。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 仅允许当前有效管理员访问后台页面、管理数据和管理操作；普通用户、禁用账号和未登录访客不得获得任何后台数据。
- **FR-002**: 后台首页 MUST 展示用户总数、有效用户数、禁用用户数、管理员数、投递总数和面经总数。
- **FR-003**: 后台首页 MUST 展示最近 7 天与 30 天的新注册和活跃用户趋势，并明确统计口径、时区和最近更新时间。
- **FR-004**: 系统 MUST 区分统计值为零、无可用数据和统计加载失败三种状态。
- **FR-005**: 管理员 MUST 能按用户名或内部邮箱进行精确或部分匹配检索。
- **FR-006**: 管理员 MUST 能按角色、启用状态和注册时间范围筛选用户，并能组合筛选条件。
- **FR-007**: 用户目录 MUST 提供匹配总数、稳定排序和分页；翻页、刷新及从详情返回时 MUST 保留检索与筛选状态。
- **FR-008**: 用户列表 MUST 展示账号标识、角色、状态、注册时间、最近登录时间和关键业务数量，并对从未登录等缺失值使用明确标签。
- **FR-009**: 管理员 MUST 能查看单个用户的账号资料、角色、状态、注册与最近登录时间、投递数量、面经数量及最近管理变更摘要。
- **FR-010**: 用户详情 MUST 允许有效管理员分页查看指定用户的投递信息、阶段、投递备注以及面经问题、回答、复盘和行动项；这些求职内容 MUST 保持只读，不得提供编辑、删除或导出入口，且列表页不得展示正文。
- **FR-010a**: 每次管理员读取指定用户的求职正文 MUST 写入不含正文的结构化安全日志，至少包含操作者 ID、目标 ID、分页、记录数量和耗时；Session、Cookie、IP、user-agent、搜索文本及求职正文不得进入日志。
- **FR-011**: 管理员 MUST 能将普通用户提升为管理员、将管理员降为普通用户、禁用有效账号或重新启用已禁用账号。
- **FR-012**: 每次角色或状态变更前，系统 MUST 展示目标账号、当前值、变更后值及影响，并要求管理员提供非空操作原因和明确确认。
- **FR-013**: 系统 MUST 阻止任何会导致平台没有有效管理员的角色或状态变更，并保持目标账号原状。
- **FR-014**: 管理员对当前账号执行降级或禁用时，系统 MUST 采用区别于普通操作的强化确认；操作成功后 MUST 立即结束其当前管理会话。
- **FR-015**: 禁用账号成功后，系统 MUST 立即使该账号所有现有登录失效并拒绝新的登录；重新启用不得恢复禁用前的登录状态。
- **FR-016**: 系统 MUST 检测基于陈旧账号状态提交的管理操作，拒绝无提示覆盖，并要求管理员基于最新状态重新确认。
- **FR-017**: 系统 MUST 防止重复提交同一管理变更，并在成功、失败或结果未知时提供明确、可恢复的反馈。
- **FR-018**: 系统 MUST 为每次角色或状态变更尝试记录事件时间、操作者、目标用户、操作类型、变更前后值、原因和结果；敏感凭据及个人求职内容不得进入记录。
- **FR-019**: 管理员 MUST 能按操作者、目标用户、事件类型、结果和时间范围组合筛选审计记录，并查看匹配总数和分页结果。
- **FR-020**: 审计记录 MUST 对后台管理员保持只读；用户标识变化或账号删除不得破坏既有事件的可辨认性。
- **FR-021**: 所有后台列表和详情 MUST 定义加载、空、成功和失败状态，并允许管理员在失败后安全重试。
- **FR-022**: 所有关键管理流程 MUST 支持键盘操作、清晰焦点、语义化标签和辅助技术可理解的状态反馈，并满足 WCAG 2.2 AA 适用标准。
- **FR-023**: 后台 MUST 在项目支持的桌面与窄屏视口中保持信息可读和关键操作可完成，不得依赖颜色作为唯一状态提示。
- **FR-024**: 所有日期时间 MUST 以 `Asia/Shanghai` 解释和展示，并在涉及统计范围或审计筛选时明确标注时区。
- **FR-025**: 在包含 10,000 个用户和 100,000 条审计事件的代表性负载下，用户目录、用户详情和审计筛选仍 MUST 满足本规格的可见响应目标。

### Key Entities *(include if feature involves data)*

- **管理员账号（Administrator Account）**: 具有管理权限且未被禁用的用户账号；可访问后台并执行受保护操作。
- **受管用户（Managed User）**: 管理员检索和处置的账号，包含账号标识、角色、状态、注册时间、最近登录时间及业务数量摘要。
- **账号访问状态（Account Access State）**: 用户当前的角色、启用状态和用于检测陈旧操作的状态版本；决定其可访问范围和登录资格。
- **管理操作（Administrative Action）**: 一次拟执行或已执行的角色/状态变更，包含操作者、目标、原因、变更前后状态与结果。
- **审计事件（Audit Event）**: 对管理操作尝试的不可编辑历史记录；即使相关账号后来改名或删除，仍保留事件发生时的可辨认快照。
- **运营摘要（Operational Summary）**: 指定统计口径与时间范围内的用户、活跃度及核心业务数量集合，并带有更新时间和数据状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 10,000 个用户的代表性数据集中，至少 95% 的用户检索、筛选、翻页和详情打开操作在 2 秒内向管理员展示完整结果或明确状态。
- **SC-002**: 至少 95% 的角色或状态变更在确认后 1 秒内展示确定结果；禁用成功后，目标账号的后续受保护请求 100% 被拒绝。
- **SC-003**: 由目标账号、角色、状态或注册时间组成的标准查找任务中，至少 90% 的管理员可在首次尝试且 30 秒内定位正确用户。
- **SC-004**: 角色变更、禁用、启用、自我操作、最后管理员保护和并发冲突的验收用例 100% 产生预期结果，且不出现未记录的状态变化。
- **SC-005**: 每一次管理变更尝试均可在审计记录中按操作者、目标和时间检索到，必填审计字段完整率为 100%。
- **SC-006**: 访客、普通用户和禁用账号的后台访问测试 100% 被拒绝，响应中不泄露用户目录、运营摘要或审计数据。
- **SC-007**: 管理员完成“定位用户并安全禁用账号”的可用性测试成功率达到 90%，且完成过程中不需要外部操作说明。
- **SC-008**: 后台关键流程通过项目支持视口的键盘操作与自动化无障碍检查，适用的 WCAG 2.2 AA 验收项通过率为 100%。
- **SC-009**: 后台主要页面在代表性移动设备和桌面环境中的第 75 百分位最大内容呈现不超过 2.5 秒，交互反馈不超过 200 毫秒，页面稳定性偏移不超过 0.1。

## Assumptions

- 本功能增强现有管理员后台，不改变公开注册只能创建普通用户、普通用户数据按所有者隔离以及首个管理员由受控流程引导的既有规则。
- 当前仅有 `user` 和 `admin` 两种角色；自定义角色、组织级权限和细粒度权限策略不在本次范围内。
- “活跃用户”默认指统计时间范围内至少完成一次有效登录的未禁用用户；所有自然日按 `Asia/Shanghai` 计算。
- 管理员查看用户业务情况仅用于支持和运营；账号详情可只读查看投递、阶段、备注和面经复盘，但简历与附件仍不在本次管理后台范围内。
- 本次不包含删除用户、代替用户编辑业务数据、批量角色/状态变更、密码重置、消息通知或审计记录导出。
- 账号身份验证、会话、用户资料、投递和面经数据已由现有系统提供；本功能依赖这些数据保持可用且归属关系正确。
- 审计事件按项目安全与运维政策长期保留；后台不提供修改或删除入口，具体归档周期由后续数据治理策略决定。
- 管理员数量较少，但用户目录按至少 10,000 个用户、审计记录按至少 100,000 条进行验收。
