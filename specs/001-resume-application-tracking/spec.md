# Feature Specification: 职迹简历投递管理

**Feature Branch**: `001-resume-application-tracking`

**Created**: 2026-08-13

**Status**: Draft

**Input**: User description: “面向个人求职者，集中管理简历投递记录、招聘状态与进展，支持搜索筛选、统计、跟进提醒及数据导入导出。”

## User Scenarios & Testing *(mandatory)*

### User Story 0 - 注册、登录与角色分流 (Priority: P0)

作为首次访问者，我可以注册普通用户账号并登录；作为管理员，我可以使用已被授予管理员角色的账号登录管理后台；系统会按角色把普通用户带到求职记录首页、把管理员带到管理后台，并阻止越权访问。

**Why this priority**: 账号身份和数据隔离是公开多用户部署的安全边界，必须先于所有投递数据读写生效。

**Independent Test**: 分别使用未登录访客、普通用户和管理员访问公开认证页、普通业务页、管理后台及业务 API，核对注册、登录、退出、角色分流、数据隔离和拒绝越权行为。

**Acceptance Scenarios**:

1. **Given** 访客提供有效且未注册的邮箱和合规密码，**When** 提交注册，**Then** 系统仅创建普通用户账号，并根据邮箱确认配置提示查收邮件或直接建立会话。
2. **Given** 普通用户提供正确凭据，**When** 登录成功，**Then** 系统导航到普通用户首页，且只能看到和操作自己的投递、统计、导入及导出数据。
3. **Given** 管理员提供正确凭据，**When** 登录成功，**Then** 系统导航到 `/admin`，可查看用户列表、账号状态和全局运营摘要。
4. **Given** 普通用户尝试访问 `/admin` 或管理员接口，**When** 系统校验会话与角色，**Then** 页面导航回普通用户首页或接口返回 `403`，且不泄露管理员数据。
5. **Given** 未登录访客访问受保护页面或接口，**When** 系统发现无有效会话，**Then** 页面导航到登录页并保留安全的站内返回地址，接口返回 `401`。
6. **Given** 已登录用户选择退出，**When** 退出完成，**Then** 会话 Cookie 被清除，后续访问受保护资源需要重新登录。

### User Story 1 - 记录和维护投递信息 (Priority: P1)

作为个人求职者，我可以快速创建一条投递记录，并在招聘过程推进时更新状态、阶段和备注，从而在一个地方保留完整、可信的求职轨迹。

**Why this priority**: 投递记录是所有检索、统计和提醒能力的数据基础；即使只实现本故事，用户也能替代分散的手工记录。

**Independent Test**: 创建仅含公司名称、岗位名称和投递日期的记录，随后补充详情、更新状态和多个招聘阶段，再查看变更历史，即可独立验证核心价值。

**Acceptance Scenarios**:

1. **Given** 用户位于新增记录界面，**When** 填写公司名称、岗位名称和有效投递日期并保存，**Then** 系统创建记录并明确提示保存成功。
2. **Given** 用户遗漏任一必填字段或输入无效日期/链接，**When** 尝试保存，**Then** 系统在对应字段附近说明问题且保留已填写内容。
3. **Given** 一条已有投递记录，**When** 用户更新当前状态或增加招聘阶段，**Then** 系统保存新值、将最新日期更新为本次变化日期，并保留可回顾的变更信息。
4. **Given** 同一公司已有一个岗位，**When** 用户为该公司创建另一岗位，**Then** 两条记录分别保存且互不覆盖。
5. **Given** 用户准备删除记录，**When** 尚未完成二次确认，**Then** 记录不会被删除；确认后系统删除记录并给出明确反馈。

---

### User Story 2 - 查找和组织投递记录 (Priority: P1)

作为个人求职者，我可以从投递列表搜索、筛选、排序和分组记录，优先关注正在进行的机会，同时清楚地区分已经结束的记录。

**Why this priority**: 当记录数量增长后，快速发现需要处理的机会是系统相较普通表格的核心优势。

**Independent Test**: 准备包含不同公司、岗位、城市、日期、状态和阶段的记录集，组合使用搜索、筛选、排序和分组，核对结果及清空条件后的恢复行为。

**Acceptance Scenarios**:

1. **Given** 列表包含多家公司和岗位，**When** 用户输入公司或岗位关键词，**Then** 系统显示不区分大小写的部分匹配结果。
2. **Given** 记录具有不同状态、阶段、城市和投递日期，**When** 用户组合多个筛选条件，**Then** 仅显示同时满足所有已选条件的记录，并清晰展示当前条件。
3. **Given** 列表同时存在进行中和结束记录，**When** 用户采用默认视图，**Then** 进行中的记录优先展示，拒绝、已放弃、已接受及无反馈记录与其明确分组。
4. **Given** 用户选择某个支持的排序字段和方向，**When** 应用排序，**Then** 当前结果按该规则稳定排列；清除条件后恢复默认视图。
5. **Given** 用户打开任一列表项，**When** 进入详情页，**Then** 可查看该记录全部字段和变更轨迹并进入编辑流程。

---

### User Story 3 - 掌握整体求职进展 (Priority: P2)

作为个人求职者，我可以查看关键统计和久未更新提醒，以了解投递规模、转化进展并及时安排跟进。

**Why this priority**: 统计和提醒将原始记录转化为行动信息，但依赖已有记录，因此位于核心录入和检索之后。

**Independent Test**: 使用日期、状态和阶段均已知的样本记录，核对各统计数值、阶段分布以及超过提醒阈值的记录集合。

**Acceptance Scenarios**:

1. **Given** 系统中有一组已知记录，**When** 用户查看统计区域，**Then** 总投递、进行中、拒绝、Offer、本周新增数量均与记录一致。
2. **Given** 某些记录经历了不同招聘阶段，**When** 用户查看阶段分布，**Then** 每个阶段统计包含所有经历过该阶段的对应记录。
3. **Given** 进行中的记录连续 7 个完整日未发生更新，**When** 用户进入系统，**Then** 该记录被标记为需要跟进并显示距上次更新的时长。
4. **Given** 一条需要跟进的记录被更新或转为结束状态，**When** 统计和提醒刷新，**Then** 该记录不再出现在需跟进集合中。

---

### User Story 4 - 导入和导出投递数据 (Priority: P2)

作为已有表格数据的求职者，我可以批量导入通用表格文件，并将全部或当前筛选结果导出，以便迁移、备份或继续分析。

**Why this priority**: 数据可迁移性降低采用成本并避免锁定，是首期明确要求，但不阻塞手工管理核心流程。

**Independent Test**: 导入同时包含有效行、无效行和重复候选行的样本文件，确认预检与结果摘要；再导出全部及筛选结果并核对字段和记录数。

**Acceptance Scenarios**:

1. **Given** 用户选择包含可识别列和有效必填值的通用表格文件，**When** 完成导入，**Then** 系统创建对应记录并报告成功、跳过和失败的行数。
2. **Given** 文件存在缺失必填值、无效日期/链接或无法识别的列，**When** 系统预检，**Then** 用户可在正式导入前看到逐行问题，且无效行不会产生不完整记录。
3. **Given** 导入内容可能与现有记录重复，**When** 系统识别相同公司、岗位和投递日期的候选重复项，**Then** 用户可选择跳过或仍作为新记录导入，系统不得静默覆盖。
4. **Given** 用户处于全部列表或筛选后的列表，**When** 选择导出，**Then** 系统生成包含完整业务字段和可读状态/阶段值的通用表格文件，且导出范围与用户选择一致。

### Edge Cases

- 公司名称或岗位名称只有空白字符时，视为未填写；保存前去除首尾空白。
- 投递日期不得晚于当前日期；最新日期不得早于投递日期，历史事件按发生日期展示。
- 同一招聘阶段不能因重复选择而在同一记录中重复出现，但可以在历史中记录再次发生的同类环节。
- 记录可从结束状态重新转为进行中；该变化必须写入历史并重新参与提醒判断。
- 搜索或组合筛选无结果时，系统显示清晰空状态并提供清除条件入口。
- 删除当前正在详情页查看的记录后，系统返回有效列表状态，不显示过期详情。
- 空数据集中的统计项均显示为 0，阶段分布和提醒区域显示有意义的空状态。
- 导入空文件、超出支持大小的文件、格式损坏文件或全部无效的文件时，不创建记录并说明原因。
- 导出结果为空时，系统明确提示无可导出记录，避免生成含义不明的空文件。
- 键盘用户可完成新增、编辑、搜索、筛选、确认删除和导入导出；焦点状态可见且错误提示可被辅助技术识别。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建、查看、编辑和删除独立的投递记录。
- **FR-002**: 每条记录 MUST 包含唯一标识、公司名称、岗位名称、投递日期、当前状态、最新日期和创建/更新时间，并可选包含工作城市、职位链接和备注。
- **FR-003**: 创建记录时，公司名称、岗位名称和投递日期 MUST 为必填；其他业务字段 MUST 可在后续补充。
- **FR-004**: 系统 MUST 支持以下当前状态：待投递、进行中、拒绝、Offer、已接受、已放弃、无反馈，且任一时刻每条记录仅有一个当前状态。
- **FR-005**: 系统 MUST 支持以下标准招聘阶段：初筛、测评、笔试、一面、二面、三面、HR 面、终面，并允许一条记录关联零个或多个已经历阶段。
- **FR-006**: 系统 MUST 允许同一家公司拥有多个岗位记录，并允许公司、岗位名称相同但投递日期不同的记录共存。
- **FR-007**: 状态或招聘阶段变化时，系统 MUST 将最新日期更新为变化日期，并保留变化类型、变化前后内容及发生日期以供回顾。
- **FR-008**: 用户 MUST 能够在详情页查看记录的所有当前信息和按时间排列的变更轨迹，并从详情页进入编辑。
- **FR-009**: 系统 MUST 校验必填值、日期关系和职位链接格式，并提供与具体字段关联的可操作错误信息。
- **FR-010**: 删除记录前系统 MUST 展示包含公司和岗位信息的二次确认；取消确认不得改变数据，完成删除后 MUST 提供明确反馈。
- **FR-011**: 系统 MUST 提供以投递记录为主体的桌面端列表，并清晰展示公司、岗位、城市、投递日期、当前状态、已达阶段和最新日期。
- **FR-012**: 用户 MUST 能够按公司名称或岗位名称进行不区分大小写的部分匹配搜索。
- **FR-013**: 用户 MUST 能够按当前状态、已经历阶段、城市和投递日期范围筛选，并组合多个不同维度的条件。
- **FR-014**: 用户 MUST 能够按公司、岗位、投递日期和最新日期排序，并切换升序或降序。
- **FR-015**: 默认列表 MUST 优先展示未结束机会，并将结束记录分组区分；结束状态定义为拒绝、已接受、已放弃和无反馈，Offer 保持为需关注的未结束机会。
- **FR-016**: 系统 MUST 保留并展示当前搜索、筛选、排序和分组条件，并允许用户一键清除条件。
- **FR-017**: 系统 MUST 统计总投递数、进行中数、拒绝数、Offer 数、本周新增数，以及每个标准招聘阶段关联的记录数。
- **FR-018**: 本周新增 MUST 按用户本地时区，以周一 00:00 至当前时刻内的投递日期计算。
- **FR-019**: 系统 MUST 将处于进行中或 Offer 状态且连续 7 个完整日没有状态、阶段或内容更新的记录标记为需要跟进，并显示最后更新日期和已间隔天数。
- **FR-020**: 记录发生更新或进入结束状态后，系统 MUST 立即重新评估其跟进提醒资格。
- **FR-021**: 系统 MUST 支持从至少一种通用表格格式导入投递记录，并在写入前展示列识别、有效行数和逐行校验问题。
- **FR-022**: 导入 MUST 支持有效行继续、无效行跳过，并在结束后提供新增、跳过和失败摘要；任何行失败不得回滚其他已成功且经用户确认的行。
- **FR-023**: 系统 MUST 将公司名称、岗位名称和投递日期均相同的导入行标记为候选重复项，让用户选择跳过或创建副本，且不得静默覆盖现有记录。
- **FR-024**: 用户 MUST 能够将全部记录或当前筛选结果导出为至少一种可由常见电子表格软件打开的格式，导出内容 MUST 包含全部业务字段。
- **FR-025**: 所有重要操作 MUST 提供明确的进行中、成功、空状态和失败反馈，并在失败时尽可能保留用户输入与当前上下文。
- **FR-026**: 除注册、登录、邮箱确认和密码恢复入口外，系统业务能力 MUST 要求有效登录会话；既有安装级数据在迁移时 MUST 归属到明确的迁移 owner，禁止变成所有用户可见的无主数据。
- **FR-027**: 关键流程 MUST 支持键盘操作、可见焦点、语义化标签和可被辅助技术识别的验证反馈，并满足适用的 WCAG 2.2 AA 标准。
- **FR-028**: 系统 MUST 在受支持的常见桌面浏览器和 1280 像素及以上视口中保持完整可用，且核心记录操作在较窄桌面窗口中不得因遮挡而无法完成。
- **FR-029**: 用户查看或操作最多 10,000 条记录时，搜索、筛选、排序和统计结果 MUST 在 1 秒内呈现给 95% 的操作；新增、编辑和删除反馈 MUST 在 1 秒内呈现给 95% 的操作。
- **FR-030**: 系统 MUST 达到项目宪章规定的用户体验性能预算：LCP p75 不高于 2.5 秒、INP p75 不高于 200 毫秒、CLS 不高于 0.1。
- **FR-031**: 系统 MUST 支持邮箱和密码注册、登录、退出、邮箱确认及密码恢复；服务端 MUST 校验所有认证输入并返回不泄露账号是否存在的失败信息。
- **FR-032**: 公开注册 MUST 只能创建 `user` 角色；`admin` 角色 MUST 由迁移、受控运维命令或已有管理员授予，客户端提交的角色值不得决定权限。
- **FR-033**: 系统 MUST 在服务端数据访问层对每个业务读写校验身份、角色与资源归属；普通用户只能访问自己的投递、阶段、事件和导入批次，管理员可按后台用例访问全局数据。
- **FR-034**: 登录成功后，普通用户 MUST 进入普通业务首页，管理员 MUST 进入 `/admin`；页面级 Proxy 只用于乐观分流，Server Action、Route Handler 和数据访问层仍 MUST 独立授权。
- **FR-035**: 管理后台 MUST 允许管理员分页查看用户账号、角色、注册时间、最近登录时间和禁用状态，并允许启用/禁用普通用户；系统 MUST 阻止管理员禁用或降级自己的最后一个有效管理员账号。
- **FR-036**: 会话 MUST 使用安全 Cookie 与服务端验证，生产环境 Cookie 必须启用 `HttpOnly`、`Secure`、`SameSite=Lax` 和合理过期策略；退出、禁用账号和凭据重置后必须使不再有效的访问失效。
- **FR-037**: 登录和注册入口 MUST 具备速率限制/CAPTCHA 接入点和统一失败反馈；日志不得记录密码、访问令牌、刷新令牌或完整 Cookie。

### Key Entities *(include if feature involves data)*

- **投递记录（Application）**: 用户向某家公司某个岗位的一次投递；包含公司、岗位、城市、职位链接、投递日期、当前状态、最新日期、备注和时间戳，并关联多个招聘阶段与变更事件。
- **招聘阶段（Recruitment Stage）**: 一次投递已经历的标准招聘环节；包含阶段类型和发生日期，同一类型可在历史上再次发生，但当前阶段集合不重复展示。
- **变更事件（Application Event）**: 对投递记录状态、招聘阶段或关键信息变化的可回顾事实；包含变化类型、前后内容和发生日期，归属于一条投递记录。
- **导入批次（Import Batch）**: 一次文件导入的预检与执行结果；包含列映射、有效/无效/重复候选行及最终新增、跳过、失败汇总。
- **跟进提醒（Follow-up Indicator）**: 从记录当前状态与最后更新时间推导出的提示，不是独立通知；包含是否需跟进和已间隔天数。
- **用户资料（User Profile）**: 与认证主体一一对应的应用资料；包含角色、显示名称、禁用状态及审计时间，不存储密码。
- **账号角色（Account Role）**: `user` 或 `admin`；公开注册固定为 `user`，管理员授予属于受控管理操作。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户能够在 60 秒内完成首条仅含必填信息的投递记录创建，且首次尝试成功率达到 90%。
- **SC-002**: 用户能够在 10 秒内从 1,000 条记录中通过搜索或筛选找到指定投递，常规搜索、筛选、排序和统计操作中 95% 在 1 秒内展示结果。
- **SC-003**: 使用已知样本数据验证时，状态、阶段、总量、本周新增及跟进提醒统计准确率达到 100%。
- **SC-004**: 所有状态和阶段变更均可在详情中追溯，抽样检查的历史完整率达到 100%，且最新日期与最近一次有效变化一致。
- **SC-005**: 对混合有效、无效和重复候选行的标准导入样本，100% 的无效行在写入前被识别，已确认有效行成功导入，且系统不静默覆盖任何现有记录。
- **SC-006**: 导出全部记录或筛选结果后，记录数和业务字段值与所选范围一致，抽样往返核对准确率达到 100%。
- **SC-007**: 用户可仅用键盘完成创建、编辑、搜索筛选、删除确认和导入导出，适用界面通过 WCAG 2.2 AA 检查。
- **SC-008**: 在最多 10,000 条记录的代表性数据集上，桌面端核心流程保持可用，并满足 LCP p75 ≤ 2.5 秒、INP p75 ≤ 200 毫秒和 CLS ≤ 0.1。
- **SC-009**: 注册、登录和退出关键旅程首次尝试成功率达到 95%，有效凭据登录及角色分流在代表性环境中 p95 ≤ 1 秒（不含外部邮件送达时间）。
- **SC-010**: 自动化授权矩阵覆盖访客、普通用户和管理员对页面/API/跨用户资源的访问，所有越权用例 100% 被拒绝且无敏感数据泄露。
- **SC-011**: 两个普通用户各自创建至少 100 条记录后，列表、详情、统计、导入和导出结果的跨用户数据混入率为 0%。

## Assumptions

- 系统升级为公开多用户账号模式；普通用户之间不共享数据，多人协作、组织/团队和细粒度自定义权限仍不在本次范围内。
- 产品首期以简体中文和用户设备本地时区展示日期；日期粒度为自然日，不要求具体时分。
- “最新日期”初始等于投递日期，之后由状态、阶段或记录内容更新触发；用户可为历史事件填写实际发生日期，但不得早于投递日期。
- “长期未更新”采用 7 个完整日作为首期统一阈值，首期不提供自定义阈值或主动消息通知，仅在系统界面提示。
- Offer 被视为仍需用户关注的活跃机会；已接受、拒绝、已放弃和无反馈属于结束状态。
- 导入至少支持一种常见表格格式，导出至少生成一种常见电子表格软件可打开的格式；具体格式和模板在规划阶段确定。
- 首期支持主流桌面浏览器；移动端专门适配、招聘网站同步、邮件解析、智能分析和外部消息通知均明确不在范围内。
- 现有单用户数据由部署者在迁移时指定一个 owner；未指定 owner 时迁移必须中止并给出修复说明，不自动归属到首个注册用户。
- 管理员账号不开放自助注册；首个管理员通过受控环境变量/运维脚本或数据库迁移引导创建，后续管理员由已有管理员授予。
