# Research: 查询性能渐进优化

## Decision 1: 以完整仓储路径补充现有微基准

**Decision**: 基准必须执行生产仓储的完整查询形状，并断言页数、总数、阶段/子项计数和 owner 隔离。

**Rationale**: 现有投递和岗位市场基准主要测量简化 SQL，不包含生产仓储的全部 JOIN、LATERAL、精确总数和结果映射，不能阻止仓储回归。

**Alternatives considered**: 只保留微基准，执行更快但覆盖不足；只测 HTTP，可观察用户延迟但难以隔离查询退化。

## Decision 2: 保留精确总数，先限定页再组装子项

**Decision**: 列表使用同一 SQL 语句中的总数子查询和有界页集合，对页集合才计算阶段、问题和行动项摘要。

**Rationale**: 这会去掉 `count(*) over()` 与全匹配阶段聚合的耦合，同时保留现有页码 UI 和精确总数契约。已有 cursor 契约继续用于 API 连续浏览，不在本轮强制改变页码交互。

**Alternatives considered**: 取消总数会破坏现有 UI；跨请求缓存私人总数会引入失效和多实例一致性成本；单纯补索引不会减少聚合数量。

## Decision 3: 分析报告每个时间范围使用一次数据库往返

**Decision**: 一次构建 owner-scoped cohort 和阶段事实，由同一条 SQL 产生指标、趋势、阶段、类型、城市与面经结果。当前周期和比较周期最多各占一个连接。

**Rationale**: 当前完整报告可并行启动多个相似查询，单用户就可接近默认业务连接池上限。合并往返能直接改善并发容量，同时共享事实口径。

**Alternatives considered**: 增大连接池会放大数据库竞争；跨请求报告缓存需要完整失效协议，留待真实流量证明必要后再引入。

## Decision 4: 岗位市场读模型只保存公共摘要

**Decision**: 按公司和“包含已关闭数据”模式保存两份公共摘要，在成功岗位同步的同一事务内刷新影响公司。列表查询另行合并当前 owner 的收藏状态。

**Rationale**: 两种公共摘要覆盖默认浏览与收藏/已关闭查看的现有口径，且不会将 owner 数据写入共享表。单公司刷新避免每个来源同步后全量重建 100,000 岗位摘要。

**Alternatives considered**: 全局物化视图刷新成本过高；请求时普通视图仍需重复聚合；把收藏放入读模型会产生高基数私有副本和隔离风险。

## Decision 5: 只根据执行计划增加索引

**Decision**: 保留已有 trigram 和 owner/date/status/type 索引，先用完整基准及 `EXPLAIN (ANALYZE, BUFFERS)` 识别排序或筛选缺口，再添加最小索引集。

**Rationale**: 复合筛选组合多，预先为每种组合建索引会影响导入、自动保存和同步写入，并且不一定被规划器选用。

**Alternatives considered**: 立即增加城市、公司、职位和表达式索引；缺少执行计划证据，不符合度量优化原则。
