# Feature Specification: 查询性能渐进优化

**Feature Branch**: `codex/006-query-performance`

**Created**: 2026-09-06

**Status**: Draft

**Input**: User description: "在新的本地分支上逐步优化查询效率，包括完整仓储性能基线、先分页后聚合、游标分页、减少精确总数成本、合并分析扫描、建立岗位市场读模型，并根据执行计划决定索引与连接参数。仅本地实施，不推送或部署。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快速浏览私人记录 (Priority: P1)

作为已登录求职者，我希望在投递和面经数据量增长后，列表首页、组合筛选和翻页仍能稳定返回，且总数、排序和阶段摘要不发生变化。

**Why this priority**: 投递与面经列表是高频核心路径，也是现有查询中最适合通过减少聚合范围获得稳定收益的部分。

**Independent Test**: 在可重复的 10,000 条用户数据上运行与生产仓储相同的列表、筛选和深页查询，核对结果集与顺序，并记录延迟。

**Acceptance Scenarios**:

1. **Given** 用户有大量投递和阶段记录，**When** 打开、筛选或排序投递列表，**Then** 只有当前页的记录需要组装阶段摘要，返回的内容、总数与顺序与优化前一致。
2. **Given** 用户连续浏览多页结果，**When** 进入后续页，**Then** 系统不得因翻页深度而持续增加丢弃记录的工作量，且不得出现重复或遗漏。
3. **Given** 用户查看面经列表，**When** 按状态、阶段、结果或问题内容筛选，**Then** 结果数量、问题数和行动项数保持准确。

---

### User Story 2 - 稳定查看分析报告 (Priority: P2)

作为已登录求职者，我希望首页摘要和周期分析在数据增长或多人同时查看时仍可以快速显示，所有统计口径保持一致。

**Why this priority**: 分析路径会重复读取相同的投递群组和阶段数据，单请求可能占用多个数据库连接，是并发增长时的主要风险。

**Independent Test**: 在固定的投递、阶段和面经数据上分别运行摘要和周期报告，验证所有指标与已有契约一致，并确认单次报告不会耗尽默认业务连接池。

**Acceptance Scenarios**:

1. **Given** 用户选择任意合法日期、城市和投递类型，**When** 生成分析报告，**Then** 总数、转化、趋势、阶段和维度指标与现有业务口径一致。
2. **Given** 多个报告请求同时进行，**When** 系统读取相同数据集，**Then** 每个报告的数据库往返和重复扫描数量受控，不影响其他交互式查询。

---

### User Story 3 - 快速浏览公共岗位 (Priority: P3)

作为已登录求职者，我希望在公共岗位增长到 100,000 条及以上后，招聘广场的默认列表和组合筛选仍然快速，且公共数据与私人收藏、投递状态保持正确。

**Why this priority**: 岗位市场是数据量最大的模块，但目前仍在已有预算内；它适合在私人核心查询和分析路径稳定后独立优化。

**Independent Test**: 在可重复的 100 家企业、100,000 岗位数据上执行默认浏览和组合筛选，验证公司聚合、状态、岗位、地点、来源和当前用户状态均保持一致。

**Acceptance Scenarios**:

1. **Given** 公共岗位已按企业聚合，**When** 用户打开或筛选招聘广场，**Then** 列表读取使用预先组装的企业摘要，不必在每次请求中重复推导全部公共状态。
2. **Given** 岗位同步产生新增、更新、关闭或重开，**When** 同步完成，**Then** 后续浏览能看到与权威岗位状态一致的企业摘要。
3. **Given** 两个不同用户浏览同一公司，**When** 其中一人收藏或记录岗位，**Then** 读模型不得把私人状态共享给另一用户。

### Edge Cases

- 查询筛选后无结果时，总数、下一页和空状态必须正确。
- 同一排序值出现多条记录时，翻页必须使用稳定的唯一标识打破平局。
- 列表在用户翻页期间发生新增、更新或删除时，不得泄露其他用户数据；允许用户刷新后看到最新排序。
- 无阶段、无面经、城市为空或已关闭岗位仍必须按现有口径返回。
- 预组装的岗位摘要在更新失败时必须保留上一个完整版本，不得返回部分更新结果。
- 新增索引或读模型后，导入、自动保存和岗位同步写入必须仍满足已有写入延迟预算。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 使用可重复、隔离且不保留测试数据的大数据基准验证真实用户查询路径。
- **FR-002**: 基准 MUST 同时记录结果正确性和延迟，不得通过减少必要的业务数据来获得更快结果。
- **FR-003**: 投递列表 MUST 在选出当前页记录后再组装阶段和活动摘要。
- **FR-004**: 列表翻页 MUST 保持稳定顺序，并为连续浏览提供不随页数线性增加工作量的定位方式。
- **FR-005**: 系统 MUST 保留现有页码、总数、筛选、排序和空状态契约；可在不改变用户可见行为的前提下拆分总数与页数据读取。
- **FR-006**: 面经列表 MUST 保持问题数、行动项数、关联阶段和总数准确。
- **FR-007**: 分析摘要与周期报告 MUST 保持现有 cohort、Offer 路径、阶段到达、面经结果和业务日期口径。
- **FR-008**: 一次完整报告读取 MUST 在默认业务连接池内为其他交互式请求保留可用容量。
- **FR-009**: 岗位市场浏览 MUST 使用可原子更新的公共企业摘要，同时在请求时只合并当前用户的收藏和已记录状态。
- **FR-010**: 岗位同步、来源管理与默认目录变更 MUST 使公共企业摘要与权威岗位数据保持一致。
- **FR-011**: 所有查询 MUST 保持 owner 隔离，不得在缓存、预聚合、日志或性能测试中泄露个人数据。
- **FR-012**: 新增数据结构或索引前 MUST 提供执行计划或等价证据，证明其对目标查询有实际价值且不使关键写入超出预算。
- **FR-013**: 实施和验证 MUST 仅在本地分支与隔离测试数据库中进行，不得推送、部署或修改服务器状态。

### Key Entities

- **分页结果**: 用户当前查询的稳定顺序记录、筛选条件、总数与后续页定位信息。
- **分析事实**: 某一投递及其阶段、面经和当前状态形成的一致统计输入。
- **公司招聘摘要**: 某一公司的公共招聘状态、岗位和地点合集、时间信息与来源摘要，不包含任何用户私人状态。
- **性能基线**: 在固定数据规模、分布和执行环境下对真实查询路径的正确性与延迟记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 10,000 条私人投递及关联阶段数据上，投递列表、筛选和连续翻页均在 500 毫秒 p95 内完成，且结果完全一致。
- **SC-002**: 在 10,000 条面经及关联问题、行动项数据上，列表、筛选和搜索均在 500 毫秒 p95 内完成。
- **SC-003**: 在 10,000 条投递数据上，摘要和周期报告读取均在 500 毫秒 p95 内完成，完整报告单次使用不超过 2 个数据库查询任务。
- **SC-004**: 在 100 家企业、100,000 条公共岗位的代表性数据上，默认浏览和组合筛选在 500 毫秒 p95 内完成。
- **SC-005**: 现有查询、owner 隔离、分析口径、岗位同步和写入契约测试 100% 通过。
- **SC-006**: 投递、面经和岗位市场的现有写入性能仍在 1 秒 p95 以内。
- **SC-007**: 用户在桌面与移动视口下仍可完成搜索、筛选、翻页、打开详情和返回列表，不需要学习新的操作方式。

## Assumptions

- 继续使用现有身份、owner 隔离、业务日期和数据库事务边界。
- 本轮不拆分前后端，不引入 Java 服务、外部缓存服务或新的部署单元。
- 优先保持精确总数和现有页码交互；只有在契约与可用性测试同步更新时才会改变用户可见的分页方式。
- 所有性能结论以隔离临时数据库中的可重复测量为准，本地单次热缓存数字不作为生产容量保证。
