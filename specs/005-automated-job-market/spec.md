# Feature Specification: 自动招聘岗位市场

**Feature Branch**: `codex/005-automated-job-market`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "在新分支实现一个自动获取企业招聘岗位并在首页集中展示的模块，不依赖手动导入。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 浏览自动更新的招聘岗位 (Priority: P1)

作为已登录求职者，我希望在首页的招聘广场查看系统自动收集并持续更新的企业岗位，以便无需逐个访问公司招聘网站也能发现机会。

**Why this priority**: 自动汇集和展示岗位是该功能的核心价值；没有这一流程，其他收藏、投递和运营能力都无法产生用户价值。

**Independent Test**: 准备若干合法可访问的招聘来源并执行自动同步，用户无需上传文件即可在首页看到按公司招聘活动聚合、并带有岗位合集、地点合集、更新时间和官方投递入口的列表。

**Acceptance Scenarios**:

1. **Given** 至少一个已启用且可访问的招聘来源，**When** 系统完成一次计划同步且用户打开首页招聘广场，**Then** 用户能看到该来源当前有效的公开招聘信息及来源信息，并且同一公司的同一招聘活动以一条记录展示，岗位和地点分别合并为合集。
2. **Given** 招聘广场中存在包含多个岗位和地点的公司招聘记录，**When** 用户按关键词、企业、地点或招聘类型筛选，**Then** 任一合并岗位或地点匹配条件时该公司招聘记录即可命中，列表清楚显示当前筛选状态和匹配内容。
3. **Given** 一个岗位在来源处被更新，**When** 下一次成功同步完成，**Then** 招聘广场显示更新后的内容和最近确认时间，且不产生重复岗位。
4. **Given** 当前没有岗位或筛选无结果，**When** 用户查看招聘广场，**Then** 页面展示可理解的空状态以及清除筛选或稍后重试的下一步操作。

---

### User Story 2 - 从公共岗位开始个人投递跟踪 (Priority: P2)

作为求职者，我希望从招聘广场打开企业官方投递入口，并可将选中的岗位记录到自己的投递管理中，以便发现岗位后继续使用 JobTrace 跟踪进展。

**Why this priority**: 它把公共岗位发现能力连接到现有的私人投递管理，是从“看到岗位”到“管理求职”的关键转化。

**Independent Test**: 用户从任意有效岗位打开官方入口，并选择记录投递；系统创建仅该用户可见的投递记录，同时公共岗位仍对其他用户可见且不包含该用户的状态。

**Acceptance Scenarios**:

1. **Given** 招聘广场中的公司招聘记录包含一个有效的统一官方投递地址，**When** 用户直接选择该列表行或卡片中的“立即投递”，**Then** 系统无需用户先进入详情，直接在新页面打开企业官方申请地址，并保留清晰的来源标识。
2. **Given** 同一公司招聘记录中的不同岗位拥有不同官方投递地址，**When** 用户选择“立即投递”，**Then** 系统在当前记录内展示岗位与投递地址的选择项，用户选定后直接在新页面打开对应官方地址，不将该公司拆成多条列表记录。
3. **Given** 用户尚未跟踪某个公共岗位，**When** 用户在公司招聘记录中选定岗位并选择“记录投递”，**Then** 系统使用可用的公司、岗位、地点和链接预填个人投递记录，并允许用户确认投递日期和状态。
4. **Given** 用户已经跟踪同一公共岗位，**When** 用户再次选择“记录投递”，**Then** 系统提示已有记录并引导用户查看现有投递，而不是静默创建重复记录。
5. **Given** 用户已将公共岗位转为个人投递，**When** 其他用户查看同一公司招聘记录，**Then** 他们看不到该用户的投递状态、备注或任何其他私人数据。

---

### User Story 3 - 收藏和回访岗位 (Priority: P3)

作为求职者，我希望收藏感兴趣的公司招聘记录并筛选收藏内容，以便稍后比较其中的岗位和投递，而不会改变公共招聘数据。

**Why this priority**: 收藏改善高信息量列表中的回访效率，但不阻塞最小可用的岗位发现和投递流程。

**Independent Test**: 用户收藏一条公司招聘记录后重新登录，仍可在“仅看收藏”中找到它；其他用户的收藏状态不受影响。

**Acceptance Scenarios**:

1. **Given** 用户查看一个未收藏的公司招聘记录，**When** 用户收藏该记录，**Then** 收藏状态立即更新并在后续会话中保留。
2. **Given** 用户拥有多个收藏记录，**When** 用户启用“仅看收藏”，**Then** 列表只展示当前用户收藏且仍可查看的公司招聘记录。
3. **Given** 收藏记录中的全部岗位后来失效或下线，**When** 用户查看收藏，**Then** 系统保留该收藏的历史可见性并明确标记整条招聘记录已失效，禁止误导性投递。

---

### User Story 4 - 监控自动同步健康状态 (Priority: P4)

作为系统管理员，我希望查看各招聘来源最近同步结果、岗位变化量和失败原因，以便发现数据停更并采取措施，而不需要手工核对岗位文件。

**Why this priority**: 自动化数据只有在可观察、可恢复时才能长期可信运行；该能力主要保障运营质量，可在用户核心流程后交付。

**Independent Test**: 模拟一个来源成功、一个来源超时和一个来源返回异常数据，管理员能够区分各自状态、查看最近结果，并安全地重新触发失败来源。

**Acceptance Scenarios**:

1. **Given** 多个启用的招聘来源，**When** 管理员查看同步状态，**Then** 每个来源均显示最近尝试时间、最近成功时间、结果、发现数量、创建数量、更新数量和失效数量。
2. **Given** 某来源同步失败，**When** 管理员查看失败详情，**Then** 系统提供足以定位问题且不包含秘密或个人数据的错误摘要。
3. **Given** 某来源处于失败状态，**When** 管理员重新触发同步，**Then** 新运行被独立记录，且不会阻塞求职者浏览已有岗位。

### Edge Cases

- 同一岗位同时出现在企业官网和第三方授权来源时，系统优先保留企业官方入口，并将其他记录关联为同一机会，而不是展示重复行。
- 同一公司同时存在校招、实习和社招，或存在相互独立的招聘批次时，系统按可识别的招聘活动分别聚合，不得把不同活动错误合并为一条。
- 同一招聘活动包含大量岗位或地点时，列表默认提供紧凑摘要和完整内容入口，不能无限撑高单行，也不能因折叠而影响搜索匹配。
- 两个同名公司、集团与子公司或不同法人主体名称相近时，系统不得仅凭显示名称将其招聘记录合并。
- 来源暂时超时、限流或返回服务错误时，系统保留最后一次成功确认的数据，标记其新鲜度，并在后续计划中重试，不因一次失败批量下架岗位。
- 来源永久移除、访问权限被撤销或明确禁止自动访问时，系统停止采集该来源，并按保留规则处理既有岗位。
- 岗位没有截止日期、发布时间、完整地点或招聘类型时，系统允许缺失字段并明确显示“未提供”，不得推断成确定事实。
- 岗位拥有多个地点或远程选项时，搜索和展示必须保留全部有效地点，不能只留下第一个地点。
- 来源重复使用岗位编号、岗位标题发生变化或岗位关闭后重新开放时，系统必须基于来源身份和内容变化保留正确的生命周期。
- 来源返回包含脚本、跟踪代码或恶意标记的正文时，系统只能展示安全内容，不得在用户页面执行来源代码。
- 官方投递链接失效或指向非安全地址时，系统禁止直接跳转并向用户说明原因。
- 同步过程中部分岗位有效、部分岗位异常时，系统导入有效记录、隔离异常记录，并报告部分成功，不得让单条坏数据破坏整批结果。
- 用户浏览列表期间发生同步更新时，当前操作不得丢失筛选条件、收藏操作或已确认的个人投递数据。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 将自动获取的公共招聘岗位与用户私人投递记录作为不同的数据集合管理，并在所有读取和写入流程中保持隐私隔离。
- **FR-002**: 系统 MUST 支持登记多个公开或已授权的招聘来源，并记录其所属企业、来源类型、原始入口、启用状态和访问约束。
- **FR-003**: 系统 MUST 按计划自动检查所有启用来源，不要求管理员上传岗位文件或逐条创建岗位。
- **FR-004**: 系统 MUST 仅从无需绕过访问控制的公开来源或已获得明确授权的来源获取数据，不得规避登录、验证码、频率限制、付费限制或其他技术管理措施。
- **FR-005**: 系统 MUST 将不同来源的数据规范为一致的公共岗位信息，至少覆盖企业名称、岗位名称、工作地点、招聘活动或批次、招聘类型、原始投递地址、来源、最近确认时间和当前有效状态。
- **FR-006**: 系统 MUST 在来源提供时保留企业性质、行业、岗位描述、招聘对象、学历要求、发布时间、截止日期和官方信息入口。
- **FR-007**: 系统 MUST 通过稳定的来源身份识别同一岗位；来源不提供稳定身份时，系统 MUST 使用可审计的岗位特征识别重复候选项。
- **FR-008**: 系统 MUST 对跨来源的重复岗位选择明确的主记录，优先使用企业官方来源，并保留其他来源的追溯关系。
- **FR-009**: 系统 MUST 区分岗位新增、内容更新、关闭、重新开放和暂时未确认，不得因单次来源失败将全部岗位判定为关闭。
- **FR-010**: 系统 MUST 自动将明确超过截止日期或来源明确关闭的岗位标记为失效，并阻止用户被引导至已知无效的投递流程。
- **FR-011**: 系统 MUST 在首页提供招聘广场，并允许已登录用户在招聘广场与现有私人投递工作区之间清晰切换；招聘广场 MUST 以“企业 + 招聘活动或批次”为列表展示单位，不得为同一活动中的每个岗位重复展示一条公司记录。
- **FR-012**: 用户 MUST 能够按关键词、企业、地点、招聘类型、有效状态、发布时间和收藏状态组合筛选公共招聘记录，并清除全部筛选；任一合并岗位或地点匹配时，其所属招聘记录 MUST 被视为匹配。
- **FR-013**: 每个有效公司招聘记录的列表行或卡片 MUST 显示醒目的“立即投递”直接入口；存在统一官方投递地址时，用户无需先打开详情即可在新页面跳转；仅存在多个岗位专属地址时，系统 MUST 在同一记录内让用户选择岗位后直接跳转，不得为此拆分公司记录。同一区域 MUST 显示数据来源、最近确认时间和有效状态。
- **FR-014**: 用户 MUST 能够收藏和取消收藏公司招聘记录；收藏关系 MUST 仅对所属用户可见，并在用户后续会话中保留。
- **FR-015**: 用户 MUST 能够从公共岗位创建私人投递记录；系统 MUST 预填已有岗位信息并要求用户确认个人投递日期和初始状态。
- **FR-016**: 系统 MUST 检测同一用户对同一公共岗位的已有投递关系，并在重复创建前提示用户查看现有记录。
- **FR-017**: 公共岗位发生更新或失效 MUST NOT 覆盖用户已经保存的投递日期、状态、阶段、备注或面试记录。
- **FR-018**: 管理员 MUST 能够查看每个来源的最近尝试、最近成功、运行结果、岗位变化计数和安全错误摘要。
- **FR-019**: 管理员 MUST 能够对单个失败来源安全地重新触发同步，且同步工作 MUST NOT 阻塞求职者浏览、筛选、收藏或记录投递。
- **FR-020**: 系统 MUST 对来源访问执行合理的频率控制、失败重试和暂停策略，并在来源撤销授权或禁止访问时停止后续采集。
- **FR-021**: 系统 MUST 对来源内容进行安全处理，避免执行外部脚本、泄露访问凭据、保存非必要个人信息或向用户提供不安全的跳转地址。
- **FR-022**: 系统 MUST 为招聘广场定义并展示加载、空结果、成功、部分数据过期和失败状态，并提供键盘可操作、可见焦点、语义化结构和满足 WCAG 2.2 AA 的适用体验。
- **FR-023**: 系统 MUST 记录每次自动同步的结果和数据变化，使运营人员能够解释某岗位为何创建、更新、失效或恢复。
- **FR-024**: 系统 MUST 允许增加新的合规招聘来源类型，而不改变用户看到的岗位字段、筛选方式或私人投递流程。
- **FR-025**: 当岗位缺少官方申请地址、地址已知失效或未通过安全校验时，系统 MUST 禁用直接投递入口并明确说明原因，不得以普通文本或其他链接冒充可用投递地址。
- **FR-026**: 系统 MUST 将同一企业、同一招聘活动或批次中的有效岗位名称去重后合并展示，并将其全部有效工作地点去重后合并展示；底层岗位身份和各自投递地址仍 MUST 可追溯。
- **FR-027**: 合并后的岗位和地点超出单行可读范围时，系统 MUST 显示简洁摘要及可操作的展开入口；展开或折叠不得改变筛选结果、收藏状态或投递目标。
- **FR-028**: 系统 MUST 提供一个受管理员权限保护的默认企业来源目录初始化入口；该操作 MUST 幂等创建目录企业和公开来源、保留已有暂停或撤销状态，并在首次初始化后自动触发活动来源同步及展示结果摘要。

### Key Entities *(include if feature involves data)*

- **企业**: 招聘主体；包含规范名称、别名、企业性质、行业、官网及其与一个或多个招聘来源的关系。
- **招聘来源**: 系统可以合法自动检查的岗位入口；包含所属企业、来源身份、原始地址、启用状态、访问约束、最近成功时间和健康状态。
- **公共岗位**: 从招聘来源获得并供所有已登录用户浏览的招聘机会；包含规范岗位字段、有效状态、时间信息、来源追溯和去重身份。
- **公司招聘记录**: 首页的聚合展示单位，代表某企业的一次招聘活动或批次；关联一个或多个公共岗位，并汇总去重后的岗位名称、地点、时间范围和投递入口。
- **岗位来源记录**: 某个公共岗位在具体来源中的原始身份与最近观察结果，用于跨来源去重、审计和生命周期判断。
- **同步运行**: 对单个招聘来源的一次自动或管理员触发的检查；记录开始和结束时间、结果、变化计数和安全错误摘要。
- **招聘记录收藏**: 用户与公司招聘记录之间的私人关系；只表达回访意向，不改变公共岗位或公司招聘记录的状态。
- **岗位投递关联**: 公共岗位与用户私人投递记录之间的关系；用于防止重复创建和回到既有投递，但不让公共数据读取私人内容。

### Scope Boundaries

**In scope**:

- 自动检查无需绕过访问控制的公开企业招聘来源和已授权来源。
- 自动规范化、去重、更新和下架岗位。
- 首页按公司招聘活动聚合的招聘广场、合并岗位与地点、组合筛选、收藏、列表直接跳转官方投递地址和创建私人投递。
- 管理员同步健康、失败诊断和单来源重试。
- 从一组已登记或自动发现且验证合规的企业招聘入口持续扩大覆盖。

**Out of scope**:

- 承诺覆盖现实世界中的每一家企业或全部未公开岗位。
- 绕过登录、验证码、反自动化措施、付费墙或访问频率限制。
- 未经授权复制其他招聘聚合产品的完整数据库。
- 代表用户自动提交简历、自动填写外部申请表或保存外部招聘平台账号密码。
- 从封闭公众号、小程序、私人群聊、图片或无法验证来源的内容中自动发布岗位。
- 在本功能中评价企业、预测录用概率或自动推荐候选人。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在首期验收数据集中，至少 100 家企业的合规公开或授权招聘来源能够无需岗位文件导入而完成自动同步，其中至少 95% 的健康来源在 12 小时内反映其公开岗位变化。
- **SC-002**: 对包含新增、更新、关闭、重新开放和跨来源重复数据的验收样本，至少 99% 的岗位被赋予正确生命周期状态，且重复展示率低于 1%。
- **SC-003**: 100% 的可见岗位都显示来源和最近确认时间；已知失效岗位不会继续显示为可正常投递。
- **SC-004**: 至少 90% 的可用性测试参与者能在 2 分钟内完成“找到符合条件的岗位并打开官方投递入口”，无需帮助。
- **SC-005**: 至少 95% 的招聘广场搜索或筛选操作在代表性负载下于 2 秒内向用户呈现完整结果，且后台同步不会使交互超出该目标。
- **SC-006**: 招聘广场代表性页面在第 75 百分位满足主要内容 2.5 秒内可见、交互反馈 200 毫秒内出现、累计布局偏移不超过 0.1。
- **SC-007**: 用户从公共岗位创建私人投递后，跨用户隐私测试中不存在公共读取私人状态、日期、阶段、备注或面试内容的情况。
- **SC-008**: 100% 的来源同步失败都有可见运行记录和不含秘密或个人信息的错误摘要；单一来源失败不会阻止用户浏览其他来源的既有岗位。
- **SC-009**: 招聘广场的核心浏览、筛选、收藏和记录投递流程通过适用的 WCAG 2.2 AA 检查，并可仅使用键盘完成。
- **SC-010**: 在包含同一公司多岗位、多地点和多个独立招聘批次的验收数据中，100% 的同批次岗位以单条公司招聘记录展示，100% 的独立招聘批次保持分离，且所有底层岗位和地点均可从聚合记录中访问。

## Assumptions

- 首期覆盖目标是至少 100 家重点企业，后续通过新增合规来源持续扩大；“所有公司”被解释为尽可能广泛覆盖公开可获得的企业岗位，而非绝对全量承诺。
- 求职者继续使用现有账号体系；招聘广场面向所有已登录用户，管理员能力沿用现有管理员权限。
- 岗位正文和属性可能不完整，系统以如实保留来源信息为原则，不通过猜测填充缺失事实。
- 官方企业招聘来源优先于第三方授权来源；第三方内容仅在授权范围内使用并保留出处。
- 首页聚合边界默认为“企业 + 可识别的招聘活动或批次”；若来源无法提供批次信息，则使用来源入口及招聘类型等可审计信息形成稳定分组，并避免跨招聘类型过度合并。
- 自动来源发现可以产生候选入口，但只有确认无需绕过访问控制或已获得授权后才可启用持续同步。
- 招聘数据主要是公开企业和岗位信息；如来源包含招聘联系人等个人信息，除非业务必要且具有合法依据，否则不采集、不展示。
- 现有私人投递、招聘阶段、分析和面试复盘能力保持兼容，公共岗位模块不得改变其既有语义和数据所有权。
