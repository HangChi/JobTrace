# Feature Specification: 面试面经记录与复盘

**Feature Branch**: `002-interview-review`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: “新增面经功能，让用户记录自己的面试内容，进行复盘反思，并与投递记录中的具体招聘阶段关联。”

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 关联阶段记录面经 (Priority: P1)

作为个人求职者，我可以从某次投递的具体招聘阶段创建面经，自动带入公司、岗位、轮次和日期，避免重复录入并准确区分同一岗位的多次面试。

**Why this priority**: 阶段关联是面经与现有投递工作台形成闭环的基础，也是用户确认面经属于哪次面试的关键。

**Independent Test**: 创建一条投递记录并补录一面和二面两个不同日期的阶段，分别创建面经，核对两篇面经显示正确的轮次和日期且互不覆盖。

**Acceptance Scenarios**:

1. **Given** 一条投递已存在可记录面经的招聘阶段，**When** 用户从阶段时间线点击“记录面经”，**Then** 系统打开面经编辑界面并预填该投递、阶段类型和发生日期。
2. **Given** 同一投递存在两个日期不同的同类阶段，**When** 用户分别为两个阶段创建面经，**Then** 两篇面经各自关联对应的阶段发生记录，并在投递详情中分别展示。
3. **Given** 用户从面经入口开始创建，**When** 用户选择投递和已有阶段，**Then** 系统只允许选择该投递下尚未关联面经的阶段，并创建一篇新的面经。
4. **Given** 用户尚未补录阶段，**When** 用户从面经入口选择投递并选择面试轮次和日期，**Then** 系统先建立对应的阶段发生记录，再打开关联的面经编辑界面。

### User Story 2 - 记录问题并完成复盘 (Priority: P1)

作为个人求职者，我可以记录面试问题、当时的回答、追问和更好的回答，并总结做得好的地方、暴露的问题及下一步行动，从而把一次面试转化为可执行的改进材料。

**Why this priority**: 结构化复盘比单纯保存一段备注更容易回看、比较和转化为下一次面试准备。

**Independent Test**: 在一篇面经中添加多个问题块、填写回答与复盘内容，添加行动项并标记完成，重新打开后核对内容、顺序和完成状态均被保留。

**Acceptance Scenarios**:

1. **Given** 用户已打开一篇面经，**When** 用户添加问题并填写分类、原始回答、追问记录和复盘后的回答，**Then** 系统按问题顺序保存全部内容，并允许继续添加其他问题。
2. **Given** 面经包含多个问题，**When** 用户调整顺序、修改或删除其中一个问题，**Then** 其他问题内容不受影响，重新进入详情后顺序和内容一致。
3. **Given** 用户填写整体复盘，**When** 用户保存亮点、待改进点和下一步行动，**Then** 面经展示复盘完成程度，并将行动项作为可单独勾选的事项呈现。
4. **Given** 面经至少有一个问题且包含改进内容或行动项，**When** 用户选择完成复盘，**Then** 面经状态变为“已完成”；否则系统指出尚缺内容并保留已填写内容。
5. **Given** 用户正在填写较长的面经，**When** 用户暂时离开编辑界面或网络请求失败，**Then** 系统保留最近一次已保存的草稿，并在重新进入时提示保存状态或提供重试。

### User Story 3 - 回顾和管理面经 (Priority: P2)

作为个人求职者，我可以从面经列表按公司、岗位、面试轮次、日期和复盘状态找到记录，并从投递详情快速回到关联面经。

**Why this priority**: 面经数量增长后，检索和状态管理决定了这些记录是否真的能在下一次面试前被使用。

**Independent Test**: 准备多个公司、岗位、轮次和完成状态不同的面经，组合搜索和筛选，打开结果并返回投递详情，核对结果范围和关联跳转。

**Acceptance Scenarios**:

1. **Given** 用户拥有多篇面经，**When** 用户输入公司名、岗位名或问题关键词，**Then** 系统显示不区分大小写的部分匹配结果，并保留当前搜索条件。
2. **Given** 面经包含草稿、待复盘和已完成状态，**When** 用户按状态或轮次筛选，**Then** 列表仅显示同时满足条件的记录，并提供清除条件入口。
3. **Given** 用户从某条投递的详情页查看面经区域，**When** 用户点击某个已关联阶段的面经，**Then** 系统打开对应面经详情，并提供返回该投递详情的路径。
4. **Given** 用户准备删除面经，**When** 用户尚未完成二次确认，**Then** 面经保持不变；确认后面经、问题和行动项一并删除并给出明确反馈。

### User Story 4 - 处理阶段变化并保护隐私 (Priority: P2)

作为个人求职者，我可以修正招聘阶段而不意外丢失复盘内容；我的面经始终只对自己可见。

**Why this priority**: 阶段记录可能因录入错误被删除或修改，面经又包含敏感的个人反思，数据关系和权限必须清晰可靠。

**Independent Test**: 关联一篇面经后修改阶段日期、删除阶段并使用另一用户访问，核对面经保留、关联状态变化和跨用户访问均符合预期。

**Acceptance Scenarios**:

1. **Given** 某阶段已关联面经，**When** 用户修改该阶段发生日期或展示信息，**Then** 面经仍关联同一次阶段并展示最新阶段信息。
2. **Given** 某阶段已关联面经，**When** 用户删除该阶段，**Then** 系统明确提示面经将解除关联但不会删除；确认后面经保留并标记为“未关联阶段”。
3. **Given** 某投递下存在面经，**When** 用户删除整个投递，**Then** 系统在确认信息中说明关联面经也会被删除，并在确认后一起删除。
4. **Given** 用户尝试访问其他用户的面经列表、详情或修改入口，**When** 系统校验身份和资源归属，**Then** 请求被拒绝且不泄露面经内容或关联投递信息。
5. **Given** 用户记录本轮结果为“通过”或“未通过”，**When** 用户保存面经，**Then** 该结果只更新本轮面经，不自动把整条投递改为 Offer、拒绝或其他终态。

### Edge Cases

- 同一投递的同一阶段发生记录最多关联一篇面经；重复点击创建入口时，系统打开已有面经而不是创建副本。
- 同一阶段类型在不同日期发生时应视为不同阶段发生记录；日期相同的重复阶段应提示已存在。
- 面经解除阶段关联后仍保留原阶段类型和面试日期快照，并允许重新关联到同一投递下其他未关联且符合条件的阶段。
- 投递被删除时必须明确说明面经会被连带删除；取消删除不得改变任何关联数据。
- 用户未填写问题但尝试完成复盘时，系统阻止完成并指出至少需要一条问题记录。
- 用户只填写“做得好的地方”而没有改进内容或行动项时，系统允许保存草稿但不能标记为已完成。
- 问题文本、回答和反思仅包含空白字符时视为未填写；字段错误应显示在对应输入附近。
- 面经列表无数据、筛选无结果、阶段尚未关联面经时，均显示可继续操作的空状态。
- 删除问题或行动项前需要确认，支持在短时间内撤销最近一次删除；删除面经本身不提供无条件恢复承诺。
- 键盘用户可完成关联、编辑、添加问题、筛选、删除确认和行动项勾选；焦点状态可见，动态保存和错误信息可被辅助技术识别。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许已登录用户创建、查看、编辑和删除自己的面经记录。
- **FR-002**: 每篇面经 MUST 归属于一条投递记录，并 MUST 保存面试轮次、面试日期、复盘状态和创建/更新时间。
- **FR-003**: 面经 MUST 能够关联投递下的一次具体招聘阶段发生记录，而不是只关联阶段类型；同一阶段发生记录最多关联一篇面经。
- **FR-004**: 系统 MUST 支持从投递详情的阶段时间线创建面经，并自动带入投递、公司、岗位、阶段类型和阶段日期。
- **FR-005**: 系统 MUST 支持从面经入口选择投递和已有阶段创建面经；已有关联面经的阶段不得再次创建副本。
- **FR-006**: 用户从面经入口选择投递、轮次和日期但尚无阶段记录时，系统 MUST 允许先补录阶段再创建关联面经。
- **FR-007**: 首期可记录面经的阶段 MUST 包括一面、二面、三面、HR 面和终面；测评、笔试等非面试阶段可在后续版本扩展。
- **FR-008**: 用户 MUST 能够为面经添加、编辑、排序和删除多个问题记录；每条问题记录可包含分类、问题文本、当时回答、追问/反馈、复盘后的回答和可选自评分。
- **FR-009**: 用户 MUST 能够填写整体复盘的亮点、待改进点和下一步行动，并能够添加、排序、编辑、勾选完成和删除行动项。
- **FR-010**: 系统 MUST 支持草稿、待复盘和已完成三种面经状态；用户可保存草稿和待复盘内容。
- **FR-011**: 面经只有在至少包含一条问题记录且包含复盘后的回答、待改进点或至少一条行动项时，才 MUST 允许标记为已完成。
- **FR-012**: 系统 MUST 自动保存长表单已成功提交的内容，并显示最近保存状态；保存失败时 MUST 保留编辑内容并提供重试。
- **FR-013**: 面经 MUST 可记录本轮结果：待反馈、通过或未通过；本轮结果 MUST 与投递当前状态分开保存，不得自动改写投递状态。
- **FR-014**: 投递详情 MUST 展示关联面经数量和每个阶段的面经状态，并为未关联面试阶段提供“记录面经”入口。
- **FR-015**: 系统 MUST 提供面经列表，并支持按公司、岗位和问题文本进行不区分大小写的部分匹配搜索。
- **FR-016**: 用户 MUST 能够按面试轮次、面经状态、本轮结果和面试日期范围组合筛选面经，并清晰看到当前条件。
- **FR-017**: 列表 MUST 默认按面试日期从近到远展示，并清晰显示公司、岗位、轮次、日期、复盘状态和本轮结果。
- **FR-018**: 用户 MUST 能够从面经详情返回关联投递详情；解除阶段关联的面经 MUST 显示“未关联阶段”并保留原阶段类型和日期快照。
- **FR-019**: 当已关联阶段的展示信息或日期被修改时，面经 MUST 继续关联同一个阶段发生记录并展示最新信息。
- **FR-020**: 删除已关联阶段时，系统 MUST 在确认信息中说明面经将解除关联但不会删除；阶段删除后面经内容 MUST 保留。
- **FR-021**: 删除投递时，系统 MUST 在确认信息中说明关联面经、问题和行动项会被删除，并在确认后级联删除。
- **FR-022**: 删除面经前系统 MUST 展示包含公司、岗位和轮次的二次确认；确认后其问题和行动项 MUST 一并删除并给出明确反馈。
- **FR-023**: 所有面经读写 MUST 要求有效登录会话并校验资源归属；普通用户不得读取、修改或删除其他用户的面经及其关联信息。
- **FR-024**: 面经内容 MUST 默认私密；首期不提供公开分享、社区浏览、点赞、评论或团队协作功能。
- **FR-025**: 系统 MUST 对必填字段、日期关系、空白文本、重复阶段关联和无效关联提供可操作的字段级错误反馈。
- **FR-026**: 所有重要操作 MUST 提供进行中、成功、空状态和失败反馈，并在失败时保留用户当前编辑上下文。
- **FR-027**: 关键工作流 MUST 支持键盘操作、可见焦点、语义化标题和可被辅助技术识别的验证及动态保存反馈，并满足适用的 WCAG 2.2 AA 标准。
- **FR-028**: 面经编辑、列表和详情 MUST 在支持的桌面与较窄视口中保持可用，不得出现无法阅读或操作的横向溢出；长文本 MUST 可换行。
- **FR-029**: 用户查看或操作最多 10,000 篇面经时，搜索和筛选结果 MUST 在 1 秒内向 95% 的操作呈现；创建、编辑、排序、删除和勾选行动项的反馈 MUST 在 1 秒内向 95% 的操作呈现。
- **FR-030**: 新增面经功能 MUST 达到项目宪章规定的用户体验性能预算：LCP p75 不高于 2.5 秒、INP p75 不高于 200 毫秒、CLS 不高于 0.1。

### Key Entities *(include if feature involves data)*

- **面经（Interview Review）**: 一次具体面试的个人记录；属于一条投递，关联一个可选的阶段发生记录，并包含面试轮次、日期、本轮结果、复盘状态和整体反思。
- **阶段发生记录（Stage Occurrence）**: 投递时间线中的一次实际招聘环节；一篇面经最多关联一条，阶段被删除时可以解除关联但不删除面经。
- **面试问题（Interview Question）**: 面经中的一个问题及其原始回答、追问、复盘回答、分类和可选评分；按照用户定义的顺序排列。
- **复盘行动项（Review Action Item）**: 从面试反思中提炼的可执行事项；包含内容、排序和完成状态，属于一篇面经。
- **面经状态（Review Status）**: 草稿、待复盘或已完成；表示当前复盘完成程度，不代表投递结果。
- **本轮结果（Round Result）**: 待反馈、通过或未通过；只表示这一次面试的结果，与投递的 Offer/拒绝状态独立。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从已有阶段时间线打开创建入口后，可在 30 秒内完成面经基础信息确认并开始记录，首次尝试成功率达到 90%。
- **SC-002**: 用户可以在 5 分钟内完成一篇包含至少 3 个问题、整体反思和 1 个行动项的面经，且重新打开后内容保存准确率达到 100%。
- **SC-003**: 在包含 1,000 篇面经的代表性数据集上，用户可以在 10 秒内通过搜索或筛选定位目标面经；95% 的搜索和筛选操作在 1 秒内展示结果。
- **SC-004**: 每个阶段发生记录与面经的关联、解除关联和重新进入详情的结果准确率达到 100%；同一阶段发生记录不会产生重复面经。
- **SC-005**: 100% 的面经删除、阶段删除和投递删除流程在确认前不改变数据，并在确认后按规定保留或删除关联内容。
- **SC-006**: 两个普通用户分别创建面经后，列表、详情、搜索、筛选和修改结果的跨用户数据混入率为 0%。
- **SC-007**: 用户可仅用键盘完成阶段关联、面经编辑、问题管理、筛选、删除确认和行动项勾选；适用界面通过 WCAG 2.2 AA 检查。
- **SC-008**: 在最多 10,000 篇面经的代表性数据集上，核心页面满足 LCP p75 ≤ 2.5 秒、INP p75 ≤ 200 毫秒和 CLS ≤ 0.1。
- **SC-009**: 参与可用性测试的用户中，至少 85% 能在没有额外说明的情况下正确理解“本轮结果”和“投递状态”的区别，并完成一次面经复盘。

## Assumptions

- 面经面向已登录的个人求职者，默认只对创建者可见；不在本期引入团队共享或公开社区。
- 一次阶段发生记录在首期最多关联一篇面经；同一阶段类型在不同日期发生时属于不同阶段发生记录。
- 面经必须属于一条投递；若从面经入口开始且没有阶段记录，系统允许用户先补录一个可记录的面试阶段。
- 阶段关联使用具体发生记录作为主关系，同时保留面经自身的阶段类型和日期快照，确保解除关联后仍可回顾。
- 删除阶段默认解除面经关联而保留面经；删除投递默认连带删除其面经，所有破坏性操作都需要明确确认。
- 本轮结果不自动驱动投递状态；用户需要在投递详情中独立维护 Offer、拒绝或重新开启等状态。
- 首期只支持文本、日期、分类、评分、结果和行动项，不包含附件、音视频、语音转写、AI 生成或外部招聘网站同步。
- 日期使用项目现有的业务日期规则，以用户本地时区解释自然日；面试日期不得晚于当前业务日期，也不得早于投递日期。
- 复用现有认证、用户隔离、投递和招聘阶段能力；面经的性能、可访问性和反馈状态遵循项目宪章与现有设计规范。
